# GPT聊天断点续作协议 V2.1

目标：换聊天不中断，不再复制几万字历史。GitHub是原稿、提示词全文、返修、确认和下一步的长期事实源。
模式：仍然完全是GPT聊天；没有GitHub Actions、定时任务、API自动保存，也不要求在网页填写Token。

## 一句恢复口令

读取 douyin-XT/继续任务.md，恢复GitHub最新状态并继续当前任务。

## 恢复顺序

1. CURRENT.json：全局当前项目、阶段、最近检查点。
2. sessions/<作品ID>/STATE.json：真实阶段、版本、用户批准与否、最新文件路径。
3. sessions/<作品ID>/交接.md：当前阻塞、下一步和重要剧情约束。
4. data/projects.json：不可变的完整冻结原稿。
5. STATE引用的最新全文版本文件、逐轮返修意见和素材链接；需要时读取checkpoints旧记录。

## 什么时候写GitHub

- 产出一轮完整图片提示词时。
- 用户反馈图片问题和生成图片返修指令时。
- 用户明确批准图片时。
- 产出视频指令或视频返修指令时。
- 用户明确批准成片时。
- 用户说“保存进度”“准备换聊天”“聊天快满了”时立即保存当前全部可保存信息。

## 保存方法：每轮文本重要成果都必须落库

1. 新一轮图片提示词存完整正文于 sessions/H30/outputs/IMAGE_PROMPT_V001.md，后续递增V002等。旧版不覆盖。
2. 用户具体反馈按轮存 sessions/H30/feedback/IMAGE_FEEDBACK_V001.md，视频同样使用 VIDEO_PROMPT 和 VIDEO_FEEDBACK 命名。
3. 写新的 sessions/H30/checkpoints/CP0002.md，记录从哪个版本前进、保存哪些全文与用户原话。
4. 同步更新 sessions/H30/STATE.json、sessions/H30/交接.md、CURRENT.json 和根目录继续任务.md。推荐一次GitHub提交，避免只提交一半。
5. 提交后重新读取GitHub main分支文件，检查阶段、版本、内容、最新路径一致，再声明 SAVED。
6. GitHub工具失败、无写权限或回读不一致时只回答 NOT_SAVED，保留当前可复制的交接摘要，不得虚构保存完成。
7. 若另一个聊天已经推进版本，应先读新的STATE并核对修订号，禁止用旧状态覆盖新状态。

## 严格门禁

- 只有用户明确说“图片满意／图片定稿”，才能由图片审查进入视频制作；把用户原话保存为批准证据。
- 只有用户明确说“视频定稿”，才能设 DONE；把用户原话保存为批准证据。
- 提示词已生成不代表图片已经生成；图片已生成不代表用户已通过。
- 新聊天无法查看旧聊天私有图片或视频时，必须请用户再次提供媒体，不得伪称看过实际像素。
- 未经用户明确许可，不把私人或未公开图像放在公开GitHub仓库。

## 固定的最终简报

有成功回读：SAVED｜作品｜阶段｜新版本｜检查点｜GitHub提交SHA｜下一步。
没有成功回读：NOT_SAVED｜缺什么｜用户下次仍需提供什么。

## 总控原则

GPT为执行者、GitHub为长期记忆、用户为图片／视频唯一审批者。网页本地进度是个人备忘，不可覆盖GitHub正式状态。
